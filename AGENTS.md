# AGENTS.md

App de pedidos para el Valle del Tiétar: frontend React 19 + Vite 8 y backend Express 4 en un único `server.js`. Código, comentarios y UI en español.

## Comandos

- `npm run lint` → `tsc --noEmit`. **No hay ESLint ni formateador**: es la única comprobación estática. También typechequea los `*.test.ts`.
- `npm run build` → `vite build`. Orden habitual: `npm run lint` → `npm run build`.
- `npm run dev` → **solo** el frontend (Vite, puerto 3000). El backend es otro proceso: `npm run server` (puerto 4000). `npm start` es equivalente a `npm run server` y sirve `dist/` si existe. Vite proxea `/api` → `http://localhost:4000`.
- `npm run preview` → sirve el build de Vite en el 4173 y hereda el proxy `/api` → 4000 (`server.proxy`), pero no arranca el backend.
- `npm test` ejecuta `node --import tsx --test "src/**/*.test.ts"` sobre las utilidades del frontend. `node --test` a secas sobre esos TS falla porque los imports no llevan extensión.
- `npm run test:api` prueba CRUD, permisos, validaciones, perfiles y sustitución de medios. Usa servidores con SQLite temporal y transporte simulado para Supabase, sin modificar servicios reales.
- `npm run test:forms` prueba los formularios React contra una API con SQLite temporal y la regresión de perfil. Usa Edge instalado en Windows o Chromium de Playwright en otros sistemas. Incluye 28 combinaciones de panel y viewport.
- `npm run test:preproduction` ejecuta lint, utilidades, API, formularios y build. El informe de cobertura y los bloqueos externos está en `reports/preproduccion-2026-10-27.md`; pasar las pruebas no certifica los pagos reales ni Hostinger.
- Smoke test de API: `curl http://localhost:4000/api/health` (devuelve `mode: "mysql" | "sqlite"`).
- `npm run test:responsive` → Playwright/Chromium sobre 10 viewports; arranca Vite en el 3000 si no responde. Solo comprueba desbordamiento horizontal de la portada. Requiere `npx playwright install chromium`.
- `npm run clean` → solo borra `dist/`. No toca el código ni la base de datos.
- `npm run optimize:assets` → regenera con `sharp` los WebP/JPEG de marca y de los juegos desde `src/assets/brand/` y `src/assets/logo.png` (no se ejecuta en el build).

## Arquitectura

- `server.js` (JS plano sin build) es todo el backend funcional. Al arrancar **intenta MySQL en Hostinger** con `.env` y, si la conexión falla, **cae a SQLite local** `data/app.db` (WAL). El modo activo vive en `databaseMode` y se ve en `/api/health`. Supabase queda reservado para el almacenamiento de fotos, vídeos, GIF y sus relaciones de medios; no sustituye la base funcional de pedidos, usuarios, negocios y pagos.
- El servidor **crea y migra su propio esquema** en ambos motores: SQLite con `sqliteSchema` + `ensureSqliteSchemaShape` (`ALTER TABLE`); MySQL con `mysqlSchema` + `ensureMySqlSchemaShape`. Tocar la BD real = tocar ese esquema.
- `database/schema.sql` es **solo documentación PostgreSQL** (el backend no soporta PostgreSQL); `database/mysql_schema.sql` es la variante MySQL/MariaDB. El servidor no ejecuta ninguno de los dos: su esquema MySQL está embebido en `server.js`. Ejecutar un dialecto en el motor equivocado da errores de sintaxis.
- Frontend: `index.html` → `src/main.tsx` → `src/App.tsx`. No hay router: la vista (`home`, `orders`, `business-dashboard`, etc.) es estado de React. Estado global en `src/context/AppContext.tsx`; tipos en `src/types.ts`; planes de suscripción estáticos en `src/data/mockData.ts`; errores de formulario en `src/components/FormErrors.tsx`.
- **No hay datos demo ni seed de localidades, negocios o productos**: el frontend arranca vacío y la API es la única fuente de esas entidades. Los datos reales se crean desde el panel de superadministración. Las categorías son catálogo de plataforma: las 15 iniciales se siembran una sola vez al crear la tabla `categories` o si existe vacía y aún no hay marcador `categories_seeded_v1` en `platform_meta`; después se gestionan desde la API y no se reponen si el superadmin las borra.
- `AppContext` centraliza las llamadas con `apiFetch` (`/api`, `Authorization: Bearer <token>`). Al montar carga localidades/negocios/productos/categorías desde la API (aunque devuelva listas vacías) y, si hay token, pedidos; los pedidos llegan por el WebSocket de sesión (`order:changed`) y, como respaldo, se refrescan cada 8 s y al recuperar el foco. `refreshBusinesses()` reemplaza la lista de negocios con la del servidor (también vacía) y la usa `AdminDashboard` antes de editar/eliminar o asignar negocios a un repartidor. Localidades, negocios, productos y categorías **no se cachean en localStorage**.
- **Arranque en portada**: la app siempre abre en la vista `home`; `authModalOpen` nace `false` (no hay ningún `useEffect` que lo autoabra sin sesión). Si un anónimo intenta pagar desde el carrito, `CartDrawer` pide sesión mediante el prop `openAuthModal`. El login de `AuthModal` funciona igual con nombre de usuario o correo.
- **Apariencia**: `.selection-glow` en `src/index.css` recoloreada a `#ff4e00` (4 capas de sombra, máx 14 px). La etiqueta `.product-banner__category` está agrandada ~60 % (14 px/22 px, padding 6px 16px) y junto a `.product-banner__dish` llevan halo naranja intenso.
- Servicios: `src/services/googleWorkspace.ts` (GIS/Calendar/Gmail) y `src/services/paymentService.ts` (ledger y checkout). Utilidades: `orderValidation.ts`, `orderVisibility.ts`, `productOptions.ts`, `imageUpload.ts`, `mediaUpload.ts`, `courierValidation.ts`. Componente compartido: `src/components/MediaView.tsx` (pinta foto o vídeo con `object-contain` para que se vea completo en el espacio asignado; acepta jpeg/jpg/png/gif y mp4 de hasta 2 s). `src/components/SensitiveInput.tsx` (campos sensibles: contraseñas, PIN de entrega e IBAN; botón mostrar/ocultar con `Eye`/`EyeOff`, `<button type="button">`). Se usa en `AuthModal`, `AdminDashboard`, `BusinessDashboard` y `CourierDashboard`.
- **Carga de medios (fotos y vídeos)**: fotos jpeg/jpg/png/gif reescaladas a máx. 800 px y calidad JPEG 0.65; vídeos mp4 de hasta 2 s recodificados a 480p, ~800 kbps, códec H.264. `processMediaFile(file)` procesa archivos de `<input type="file">`; `processMediaUrl(url)` procesa URLs pegadas (http/https o data:). `MEDIA_ACCEPT` incluye `.jpg,.jpeg,.png,.gif,.mp4` y sus MIME types. La integración prevista debe guardar el binario en Supabase Storage y la relación/URL segura en Supabase; mientras no esté implementada, el backend actual acepta URLs o data URLs con sus límites existentes. Todos los inputs de archivo tienen un campo de texto adicional para pegar una URL o ruta de archivo.
- **Lazy loading**: `src/hooks/useIntersectionObserver.ts` detecta cuándo un elemento entra al viewport; `src/components/LazyMediaView.tsx` envuelve `MediaView` con carga diferida, skeleton y altura fija para evitar layout shift. Se usa en `HomeView.tsx` (categorías, banners de comercios, productos destacados) y `BusinessDetailView.tsx` (imágenes de productos).
- **MediaView**: acepta `defaultSrc` (logo de PideTietar por defecto) y `showLoading`; muestra el logo por defecto si `src` está vacío o la carga falla.
- **PideTietar Play (catálogo de juegos)**: `src/games/registry.ts` declara los juegos (id, portada en `public/assets/games/<id>/icon.png`, categoría, color y carga `lazy`). Hoy están disponibles Reparto Express (`src/games/RepartoExpress/`), Burbujas (`src/games/pide-bubble/`, portado desde el proyecto suelto de Bubble), Blocks (`src/games/pide-blocks/`) y Rompecabezas (`src/games/pide-rompecabezas/`, con las fotos del valle en `public/assets/games/rompecabezas/tietar/` cargadas en runtime). `GamePlayer` recibe el `onClose` del juego y guarda el componente con `setComponent(() => comp)`: si se guarda la función directamente, React la trata como actualizador de estado y la invoca con `null`, lo que dejaba la pantalla en blanco al abrir cualquier juego. `GameCardsRow` pinta la cabecera «PideTiétar Play» (estilos `.pide-play-header` al final de `src/index.css`) entre el catálogo y las portadas. Al superar el quinto nivel, cada juego muestra la celebración compartida `GameCelebration` (`src/components/GameCelebration.tsx` + `.css`): confeti con `canvas-confetti` (`zIndex: 400`), 10 globos y 16 serpentinas CSS, tarjeta con «Seguir jugando» y cierre con Escape; respeta `prefers-reduced-motion`. Las CSS propias de cada juego (`.blocks-game`, `.bubble-game`, `.rompecabezas-game`) se limitan a su contenedor para no tocar el resto de la app, y ninguno guarda datos en `localStorage` (solo `sessionStore`). Los juegos usan `canvas-confetti`, así que la CSP de `server.js` incluye `worker-src 'self' blob:`; si se endurece, el confetti deja de animarse. **Burbujas en móvil**: `GameCanvas.tsx` limita el `devicePixelRatio` del canvas a 2 (2,5 en escritorio), pre-renderiza cada burbuja, su resplandor, las chispas y el fondo en lienzos cacheados (`spriteCacheRef`, `glowCacheRef`, `backdropCacheRef`) y los estampa con `drawImage`; el bucle de `requestAnimationFrame` no depende de la puntuación ni de las burbujas restantes (las lee de `loopApiRef`, que se reasigna en cada render) para no reiniciarse en cada explosión, y el movimiento usa `step = clamp(dt*60, 0.5, 2)` para ir igual de rápido a 30, 60 o 120 Hz. Las partículas se dibujan con sprite aditivo (`lighter`, sin `shadowBlur`), se limitan a `MAX_PARTICLES = 220` y a 8 por explosión en pantallas pequeñas, y las etiquetas de puntuación se limitan a 3 y usan contorno en lugar de sombra. No vuelvas a meter `ctx.shadowBlur` ni degradados por burbuja dentro del bucle: es lo que hacía que el juego se congelara medio segundo al reventar una cadena. **Rejilla**: `GRID_COLS = 9` y `BUBBLE_RADIUS = 19` en `utils/bubblePhysics.ts` porque con 10 × 40 px = 400 no cabía en el lienzo (376 CSS en móvil, 349 en escritorio) y se recortaban las dos columnas de los extremos.

- **Space Invaders**: `src/games/SpaceInvadersGame.tsx` + `.css`. Lienzo de 700 × 912 (760 × 1,2: creció un 10 % por arriba y otro 10 % por abajo) con el aspecto del icono: fondo índigo/morado cacheado en `paintBackdrop` (nebulosas, planeta con anillos, galaxia espiral, 96 estrellas, rejilla neón en perspectiva con horizonte al 80 % del alto y viñeta), 8 destellos animados en `drawSparkles` y 32 aliens (8 × 4) dibujados como bitmaps pixelados de 11 × 8 con `PIXEL = 4` y dos fotogramas (`INVADER_A`/`INVADER_B`), pre-renderizados con glow en `spriteCache` por fila y fotograma. Cada fila usa la paleta del icono (`ROW_COLORS`): naranja, verde, rosa y cian. La nave es una figura dibujada a mano (casco blanco con degradado, franja y alas rojas, cabina cian y llama de motor que parpadea). El **dashboard** se pinta en el lienzo (`drawDashboard`): barra translúcida de 88 px con PUNTOS (38 px, halo cian), RÉCORD (38 px, halo rosa), **NIVEL n/5** y cinco mini-naves de vidas con neón (`START_LIVES = 3`, `MAX_LIVES = 5`), más avisos con `drawMessage` y destello rojo `drawHitFlash`. Los aliens llevan **núcleo neón**: el sprite se rellena con el color de la fila, un píxel interior en tono claro (`ROW_COLORS[].light`) y halo reforzado; la nave del jugador tiene aura cian y contorno neón, y el kamikaze, halo pulsante. **Niveles**: `MAX_LEVELS = 5` y `prepareLevel` reconstruye la formación en cada uno. La **marcha lateral** sube un 10 % por nivel con `factorNivel = 1 + 0,1 × (nivel − 1)` (`MARCHA_BASE = 30 px/s`, más `MARCHA_ACELERON = 48` conforme se diezma la formación), igual que el zigzag y la bajada de los kamikazes (`vy = 120 × factor`) y los disparos enemigos (`220 × factor`). La **bajada continua** del muro sube el doble, `BAJADA_POR_NIVEL = 20 %` sobre `DESCENSO_BASE = 5 px/s` → **5, 6, 7, 8 y 9 px/s** (medido 5,17 / 6,00 / 7,00 px/s en los niveles 1–3). La formación ya **no** da el salto clásico de 14 px al rebotar en el borde: desciende de forma continua, que es la única manera de que la velocidad de bajada sea exactamente la de cada nivel. **Kamikazes**: cada nivel suelta `level` naves (`diversLeft`), una cada 6–9 s; `createDiver` las lanza cerca de la nave del jugador y bajan zigzagueando (`amp`/`freq`/`phase` aleatorios) intentando chocar; si chocan restan una vida y si salen por abajo desaparecen; derribarlas da `BONO_KAMIKAZE = 150` con aviso «¡Bono +150!». **Recompensa**: al superar cada nivel se gana una vida (`state.lives = Math.min(MAX_LIVES, lives + 1)`) con aviso «¡Nivel n superado! · +1 vida»; la pausa entre niveles es de 1,8 s. Controles: botones translúcidos de izquierda y derecha (`controlsRef` con `left`/`right`) y de disparo (`fire`), además de arrastre sobre el lienzo (`pointerTarget`) y teclado A/D, flechas y Espacio; la nave vive en `SHIP_Y = HEIGHT - 130` para no quedar bajo los botones. `INVULNERABLE_MS = 1200` con parpadeo tras perder una vida y reinicio de los disparos enemigos. La partida se pierde si los aliens alcanzan la nave o se agotan las vidas, y se gana al limpiar el nivel 5; entre niveles hay una pausa de 1,8 s con aviso. `saveScore(score, level)` guarda el nivel alcanzado. **Tamaño del lienzo**: lo fija un `ResizeObserver` en el componente (`escala = min(ancho / 700, alto / 912)`, píxeles CSS en `style`); no lo resuelvas con `height: auto` + `max-height`, porque el navegador aplasta el dibujo (se midió 700 × 847 estirado en escritorio). Con la proporción correcta queda en 650 × 847 en escritorio y 390 × 508 en móvil. Al principio de cada fotograma hay `setTransform` de seguridad, y el id de `requestAnimationFrame` (`frame`) no debe confundirse con el fotograma de animación de los aliens (`frameAlien`).

Al terminar el nivel 5 y el 12 se lanza `GameCelebration`. La puntuación se envía con `serverLevel` (1–5), porque el servidor valida `level_reached` entre 1 y 5. La portada `public/assets/games/classic-puzzle/icon.jpg` es la original del repositorio (paisaje con rejilla 4×4 numerada): es fija y no se debe regenerar ni sustituir.
- **Memory (`src/games/MemoryHtmlGame.tsx` + `.css` + `memoryLevels.ts`)**: juego de parejas con **10 niveles** que van de **8 a 24 parejas** (16–48 cartas): el nivel 1 es un tablero **4×4** (8 parejas) y la cuadrícula crece nivel a nivel (6×3, 5×4, 6×4, 7×4, 8×4, 6×6, 8×5, 9×5 y 8×6) con un tema de dibujos distinto por nivel (frutas, animales, mar, espacio, tiempo, deportes, vehículos, música, fantasía y golosinas); los símbolos son emoji grandes (64 % de la carta) para que la carta descubierta se vea como los dibujos del icono. **Los niveles se desbloquean en orden**: el 1 siempre abierto y cada uno se abre al completar el anterior (`isLevelUnlocked`), y al volver se reanuda en el primer pendiente (`firstPendingIndex`). El progreso vive en el servidor (`game_progress`, por usuario y juego) con `sessionStorage` como caché y respaldo (`pidetietar-game-memory-html-completed-v1`), y el récord en `…-best-v1`; ambos juegos usan el hook `useGameProgress`. La puntuación se envía con `serverLevel` 1–5 (`serverLevelFor`) porque el servidor valida `level_reached` entre 1 y 5; `GameCelebration` se lanza al superar el nivel 5 y el 10. El diseño imita la portada: fondo índigo con rejilla neón, marco con degradado naranja→violeta→cian, dorsos morados con cuadros y caras blancas con el dibujo; el botón de empezar y el panel de nivel superado se pintan como capa sobre el tablero (`.pidetietar-memory-html__overlay`) con el tablero atenuado (`.is-dimmed`) para no tener que hacer scroll, y «Reiniciar» vive en la cabecera. Columnas por nivel en `memoryLevels.ts` (`columns` en escritorio y `compactColumns` de 4 a 6 en < 600 px); el ancho del tablero se limita con `calc((100dvh - 320px) * columnas / filas)` (y un suelo de 240 px) para que cada nivel quepa entero en la pantalla sin scroll, con las cartas lo más grandes posible. El panel se centra en vertical con `margin-block: auto` y la última fila incompleta se centra porque el tablero es flex. La lógica pura (reparto, desbloqueo, puntuación, columnas) está en `memoryLevels.ts` y se prueba en `memoryLevels.test.ts`.
- **Navegación de PideTiétar Play**: la sección usa tres rutas en el hash —`#juegos` (fila de portadas), `#juego/<id>` (ficha con ranking y «Jugar ahora») y `#jugar/<id>` (partida)— que `App.tsx` sincroniza con `pushState`/`replaceState`. Al bajar un nivel se apila una entrada y al subir se retrocede con `history.back()`, así que el botón «Volver» de `GamePlayer` y el atrás del navegador hacen **un solo paso atrás** (partida → ficha → portada) en lugar de saltar a la portada. Los botones internos de cada juego (`Salir`, la X y `Escape`) siguen llamando a `onClose`, por lo que heredan ese paso atrás. Recargar en `#juego/<id>` restaura la ficha y en `#jugar/<id>` la partida (empieza de cero); sin sesión esas rutas vuelven a la portada y el hash se limpia. La cabecera de la ficha (`GameDetailView`) muestra siempre la marca **«PideTiétar - Play»** en blanco con el icono de mando; el nombre del juego va debajo de la portada.
- `server.js` sirve `dist/` estáticamente si existe **al arrancar**: un build viejo puede confundir tus pruebas en el 4000. Si no existía, el catch-all devuelve JSON hasta reiniciar.
- No hay CORS, helmet ni rate limiting: el frontend debe usar el proxy de Vite en desarrollo o el mismo origen en producción.
- Medios en Supabase: `POST /api/media` sube un data URL al bucket configurado y crea la relación en `public.media_assets`; `GET /api/media?entityType=...&entityId=...` consulta relaciones; `DELETE /api/media/:id` elimina archivo y relación con autorización. La migración está en `database/supabase_media.sql` y usa como `entity_id` los IDs externos de Hostinger.

## Auth, roles y permisos

- Roles: `CLIENT`, `BUSINESS_ADMIN`, `BUSINESS_COURIER`, `PLATFORM_COURIER`, `SUPERADMIN`.
- Sesión: token HMAC-SHA256 (no JWT) con `sid`, `sub`, `role`, `businessId`, `iat`, `exp`, vinculado a `auth_sessions` en SQLite/MySQL. TTL absoluto 168 h (`SESSION_TTL_HOURS`), pero la sesión se revoca tras 10 s de desconexión (`SESSION_DISCONNECT_MS=10000`). Presencia por WebSocket `/api/auth/session`, con identificación en el primer mensaje y ping/pong nativo. Se acepta el token en `Authorization: Bearer ...` o `x-auth-token`. Los tokens antiguos sin `sid` requieren nuevo login. `requireAuth` / `requireRole(...)` validan firma y sesión activa; `requireSuperAdmin` = `requireRole("SUPERADMIN")`.
- Concurrencia: una conexión por cuenta por defecto. Solo `BUSINESS_ADMIN` admite `app_users.additional_connections`; solo SuperAdmin los consulta/autoriza en `GET/PUT /api/users/:id/connections` y en el botón «Conexiones» de su tabla de negocios. Un segundo dispositivo sin cupo recibe 409 `SESSION_LIMIT_REACHED`. El mismo `deviceId` de la pestaña reutiliza su sesión al recargar. La reserva se serializa por cuenta en una transacción.
- Contraseñas con bcrypt. `POST /api/auth/register` siempre crea `CLIENT` y exige `address` (dirección de entrega) en el cuerpo; devuelve 400 `VALIDATION_ERROR` si falta. El superadmin conserva el acceso de emergencia con `SUPERADMIN_PASSWORD`; la sesión debe registrarse en MySQL o en SQLite local para aplicar el mismo límite de conexiones. El identificador de ese acceso está fijado en `server.js` y **no** lo cambia `SUPERADMIN_USERNAME` (esa variable solo bautiza el usuario sembrado en la BD). En producción define siempre `SUPERADMIN_PASSWORD` y `SESSION_SECRET`.
- `POST /api/auth/login` acepta `username` o `email`. Si la cuenta tiene `password_change_required`, responde 403 `PASSWORD_CHANGE_REQUIRED`; `POST /api/auth/change-password` permite fijar la nueva sin sesión presentando identificador + contraseña actual.
- **Recuperación de contraseña**: `POST /api/users/:id/request-password-reset` (solo superadmin) envía a la cuenta un enlace de un solo uso (`#restablecer-clave?token=…` sobre `APP_URL`, 60 min por `PASSWORD_RESET_TTL_MINUTES`); `POST /api/auth/reset-password` (público) consume el token y fija la nueva clave. El token es aleatorio de 32 bytes y en BD solo se guarda su SHA-256 (`password_reset_hash` + `password_reset_expires_at`, limpiados al usarlo o expirar); token inválido, usado o caducado → 400 `INVALID_RESET_TOKEN` (mismo error en los tres casos, sin revelar el estado de la fila). Sin SMTP el enlace vuelve en la respuesta para copiarlo. Panel: "Recuperar Clave" en la tabla de negocios.
- `GET /api/orders` exige sesión y filtra en servidor:
  - `SUPERADMIN` y `PLATFORM_COURIER`: todos (el de plataforma cubre el valle).
  - `BUSINESS_ADMIN`: solo su `business_id`.
  - `BUSINESS_COURIER`: pedidos de sus negocios asignados (`courier_business_ids`) **o** asignados a él (`courier_id`).
  - `CLIENT`: `customer_id` propio; los pedidos antiguos sin `customer_id` se aceptan por email.
- Los endpoints `/api/debug/*` son solo de superadmin.

## Reglas de negocio

- **IBAN**: la cuenta bancaria es del negocio (`businesses.account_number`) y, para repartidores, un dato de cobro (`app_users.account_number`). El cliente no la maneja (`AuthModal` la tiene eliminada a propósito). El dueño edita la de su negocio desde "DATOS DEL NEGOCIO"; la del repartidor solo la configura el superadmin y el dueño no puede verla ni editarla, solo confirmar al repartidor.
- **Negocios**: `GET` público; alta solo `SUPERADMIN` (crea negocio + horario + cuenta del propietario en una transacción); edición `SUPERADMIN` o el propietario de ese negocio; borrado `SUPERADMIN`, bloqueado con 409 `BUSINESS_HAS_ORDERS` si hay pedidos.
- **Usuarios**: `GET /api/users` solo superadmin y dueño de negocio (este ve únicamente sus `BUSINESS_COURIER`). El dueño solo crea repartidores de su negocio y con confirmación `PENDING`; el superadmin puede crear cualquier rol. `PUT /api/users/:id` permite al propio usuario, al superadmin o al dueño confirmar a su repartidor (este último solo `courierConfirmation`). `DELETE` solo superadmin y no permite borrarse a sí mismo.
- **Panel de negocio**: un único formulario "DATOS DEL NEGOCIO" que incluye el bloque "Cuenta del responsable" (avatar, nombre, correo, teléfono y contraseña). Ya no existe el modal "Configuración del administrador". El bloque de perfil solo se guarda si el usuario en sesión es propietario del negocio (`currentUser.businessId === business.id` y no `SUPERADMIN`). El avatar de la cabecera para `BUSINESS_ADMIN` abre solo el editor de avatar (`AvatarEditorModal`); los demás roles conservan el perfil completo de `AuthModal`.
- **Repartidores**: `courier_confirmation` ∈ `PENDING` | `BUSINESS_EMAIL` | `SUPERADMIN`; `BUSINESS_COURIER` necesita al menos un negocio. La ficha guarda teléfono, dirección y DNI/NIE en `app_users.phone/address/dni`; el alta exige esos tres datos en la UI y la edición permite completarlos. El panel de repartidor exige email verificado **y** confirmación (`BUSINESS_EMAIL` o `SUPERADMIN`) en el frontend. En el panel de superadmin el alta vive detrás del botón "Actualizar" (desplegar/ocultar), la clave se puede mostrar/ocultar y los errores del servidor se pintan en su campo (`toCourierFieldErrors`).
- **Pedidos**: importes siempre en **céntimos enteros**. Comisión de plataforma: 5 % del subtotal + 20 % del envío; `business_payout` y `courier_payout` se guardan en el pedido. El PIN de entrega lo genera el cliente y el servidor lo valida antes de aceptar `DELIVERED`. `POST /api/orders` y `PUT /api/orders/:id` aceptan camelCase y snake_case; las mutaciones comprueban el ámbito del negocio y bloquean cambios financieros posteriores para roles no autorizados. La creación todavía debe evolucionar para calcular importes exclusivamente en servidor.
- **Registro de cliente**: el alta (`POST /api/auth/register`) exige `localityId` (selector de localidad en el frontend) y `address`. La cesta del carrito se vacía al cerrar sesión y al iniciar una nueva sesión de cliente. Los formularios (registro, cesta) se limpian al cerrar y volver a abrir.
- **Catálogo**: `GET /api/products` público; `POST/PUT/DELETE` solo `SUPERADMIN`/`BUSINESS_ADMIN` y el servidor comprueba que el producto pertenece al negocio de la sesión. Las mutaciones de localidades también admiten `BUSINESS_ADMIN` sin comprobar ámbito. `POST/PUT /api/products` **sí validan que `category_id` exista** antes de escribir: sin categoría o con una inexistente devuelven 400 `VALIDATION_ERROR` con `errors.category_id` (MySQL tiene FK real a `categories`).
- **Categorías**: `GET /api/categories` público; `POST/PUT/DELETE /api/categories` solo `SUPERADMIN`. La tabla `categories` guarda `id`, `name`, `slug` único, `icon_name` e `image_url`. El gestor está en `CategoryManagerModal` y se abre desde `AdminDashboard` y desde `BusinessDashboard`. No se puede borrar una categoría usada por `businesses.category` o `products.category_id` (409 `CATEGORY_IN_USE`); un slug repetido devuelve 409 `CATEGORY_EXISTS`.
- **Email**: correos con **plantilla de marca compartida** en `server.js`: `renderBrandEmail` (HTML con estilo inline, cabecera oscura degradada, franja "Valle del Tiétar · Ávila", logo `public/Logo.png` embebido como adjunto `cid:pidetietar-logo` para que se vea aunque el cliente bloquee imágenes remotas) y `sendBrandEmail` (envío común que prueba el SMTP preferente y cae a los puertos alternativos 587/465). Hay tres correos: **bienvenida** (`sendWelcomeEmail`, al crear cualquier cuenta desde registro o panel, texto según rol y CTA "Entrar y explorar" hacia `APP_URL`, sin bloquear la respuesta), **verificación** (código en caja naranja, asunto con el código delante) y **recuperación** (botón CTA con letras `#8bca60` + enlace copiable). Sin SMTP configurado el código/enlace se devuelve en la respuesta; el arranque lo refleja en el log (`SMTP configurado ✔ host=…` y `Logo del correo: … (encontrado)`). Pero `createUser` inserta `email_verified = 1`: las cuentas nuevas nacen verificadas y el flujo de verificación no bloquea el alta; `send-verification-email` vuelve a marcar la cuenta como no verificada hasta introducir el código.
- **Pagos y Google**: `paymentService.ts` está simulado (IDs fake, sin Stripe/PayPal real); `googleWorkspace.ts` puede usar GIS real con `VITE_GOOGLE_CLIENT_ID`, pero sin token válido cae a enlaces de Calendar y logs de Gmail. No los presentes como integraciones reales sin configurar claves.
- **Puntuaciones del minijuego**: `GET /api/game/score?game=`, `GET /api/game/leaderboard?game=&limit=` y `POST /api/game/score` exigen sesión (`requireAuth`); el invitado solo guarda su récord de pestaña. Existe además `GET /api/game/leaderboard/public?game=&limit=` (solo lectura, sin sesión) que devuelve `{ game, leaders }` con `position`, `name`, `avatarUrl`, `score`, `levelReached` y `playedAt` para mostrar el top al invitado; no expone `userId` ni el puesto del autenticado. `POST` acepta camelCase o snake_case, valida `score` entre 0 y 100 000 y `level_reached` entre 1 y 5 (400 `VALIDATION_ERROR` con `errors.score` / `errors.level_reached`). La tabla `game_scores` guarda todo el histórico; el ranking agrega la mejor puntuación por usuario, ordena por puntos y posición de llegada, limita a 25 filas y no devuelve avatares `data:` (solo `http(s)://`).
- **Progreso de niveles**: `GET /api/game/progress?game=` y `POST /api/game/progress` exigen sesión y trabajan sobre la tabla `game_progress` (clave `user_id, game_id, level`). Juegos admitidos: `memory-html` (niveles 1–10) y `classic-puzzle` (1–12); cualquier otro devuelve 400 `VALIDATION_ERROR` con `errors.game` y un nivel fuera de rango 400 con `errors.level`. La lectura devuelve `{ game, maxLevel, levels }` ordenado y el `POST` es idempotente (`INSERT OR IGNORE` / `INSERT IGNORE`). El frontend lo consume con `useGameProgress` (`src/games/useGameProgress.ts`), que fusiona el avance del servidor con `sessionStorage` y lo envía al completar cada nivel.

## Trampas

- **localStorage no guarda datos de sesión**: token, pedidos, cesta, token de Google, `deviceId` y el récord/nivel del minijuego se guardan en `sessionStorage` y se limpian al salir. `browserSession.ts` elimina los restos personales de `localStorage` al cargar y en `pagehide`. F5 conserva la sesión, pero reabrir o restaurar una pestaña que salió de la app exige nuevo acceso. Las pruebas que inyectan un token deben usar `sessionStorage`. Solo las preferencias (tema) y el marcador de limpieza de datos demo quedan en `localStorage`. Localidades, negocios, productos y categorías siguen viniendo de la API; se conserva `mergeOrderLists` y el refresco de pedidos cada 8 s.
- **MySQL y categorías**: `database/mysql_schema.sql` define `fk_products_category`; sin una fila válida en `categories` el alta de producto falla. No uses IDs fijos como `hamburguesas` ni el antiguo `"general"`: el formulario debe elegir una categoría de `/api/categories`. El arranque siembra las 15 iniciales si la tabla está vacía y no existe `categories_seeded_v1` en `platform_meta`; después no las repone.
- `loginAs` y la restauración de sesión **no inventan** direcciones ni suscripciones: usan lo que envíe el backend y dejan valores neutros si faltan. El backend **no persiste** `addresses` ni `subscriptionPlan`; no los uses como datos reales.
- Los pedidos locales se fusionan con los remotos (`mergeOrderLists`) y hay actualizaciones optimistas con rollback; no dupliques esa lógica ni elimines el refresco periódico.
- **Solo una instancia del backend en el puerto 4000**: si `npm run server` falla con `EADDRINUSE`, otro proceso viejo sigue corriendo con código antiguo (un servidor arrancado antes de un cambio no recarga plantillas ni lógica). Lo mata con `netstat -ano | findstr :4000` + `taskkill //PID <pid> //F`.
- `node:sqlite` (`DatabaseSync`) exige **Node ≥ 22.5**; `package.json` ya lo declara en `engines`. Rechaza bindings booleanos: pasa siempre `Number(...)`.
- Los handlers async de Express se envuelven globalmente (línea ~24) para reenviar rejections a `next()`; no elimines ese wrapper ni el middleware de errores de 4 argumentos. También hay `unhandledRejection`/`uncaughtException` como red de seguridad.
- Límite `express.json({ limit: "2mb" })`: las imágenes van como data URL o `http(s)://` sin espacios. `fileToDataUrl` reescala a ~900.000 caracteres; respeta ese margen para no provocar 413.
- `vite.config.ts` admite `DISABLE_HMR=true` para desactivar HMR y file watching durante ediciones; el watcher ignora `data/`, `*.db*` y `dist/` (la BD se escribe en cada pedido y recargaba la página).
- `data/` está excluido de git (`data/*.db*`, `data/.session_secret`): no subas la base de datos ni el secreto de sesión.
- La contraseña histórica por defecto (`INSECURE_DEFAULT_PASSWORD` en `server.js`) está marcada como insegura: al arrancar, las cuentas que la usan reciben `password_change_required = 1`. No la reutilices en datos de prueba ni la copies a la documentación.
- `firebase-applet-config.json` y `metadata.json` son restos de AI Studio; no hay SDK de Firebase ni Gemini en el código.
- **Saltos de línea (LF/CRLF)**: el repositorio incluye `.gitattributes` con `* text=auto eol=lf` para evitar el warning de Git en Windows (`LF will be replaced by CRLF`). Los archivos ya se renormalizaron a LF con `git add --renormalize .`. No edites `.gitattributes` ni conviertas archivos a CRLF; si aparece el aviso, ejecuta `git add --renormalize .` y commitea.

## Contrato de errores de la API

- Validación: `400 { code: "VALIDATION_ERROR", message, errors }`. `errors` suele usar **snake_case** (columnas reales de la BD), pero usuarios y cuenta del propietario usan camelCase (`fullName`, `ownerUsername`, `courierBusinessIds`, etc.).
- El frontend los traduce a campos camelCase del formulario dentro de `src/components/FormErrors.tsx` (`owner_username`/`ownerUsername` → `adminUsername`, etc.). Si añades un campo nuevo, mápalo ahí.
- Códigos de dominio: `INVALID_CREDENTIALS` (401), `PASSWORD_CHANGE_REQUIRED` (403), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `USER_EXISTS` (409), `BUSINESS_HAS_ORDERS` (409), `CATEGORY_EXISTS` (409), `CATEGORY_IN_USE` (409), `INVALID_CODE` (400), `INVALID_DELIVERY_PIN` (400), `INVALID_RESET_TOKEN` (400), `MEDIA_STORAGE_UNAVAILABLE` (503), `MEDIA_UPLOAD_FAILED` (502), `MEDIA_RELATION_FAILED` (502), `MEDIA_DELETE_FAILED` (502), `EXPIRED_CODE` (410), `FOREIGN_KEY_CONFLICT` (409), `PAYLOAD_TOO_LARGE` (413), `INTERNAL_ERROR` (500).
- Algunas rutas antiguas (p. ej. `PUT /api/localities/:id` sin campos) devuelven `{ success: false, message }` sin `code`; no asumas que todo error trae `errors`.

## Entorno

- `.env.example` documenta `PORT`, `DB_PATH`, MySQL (`MYSQL_*` o `DB_*`), `SUPERADMIN_*`, `SESSION_SECRET`, `APP_URL`, `PASSWORD_RESET_TTL_MINUTES`, claves Stripe/PayPal, `VITE_GOOGLE_CLIENT_ID` y `SUPABASE_*`.
- `.env.example` incluye `SESSION_TTL_HOURS`, `SESSION_DISCONNECT_MS` y las variables `SMTP_*` (también se aceptan los alias `EMAIL_*`). El código además lee `EMAIL_VERIFICATION_TTL_MINUTES`.
- Sin MySQL disponible (Hostinger rechaza la IP con `Access denied`) el arranque **cae a SQLite silenciosamente**: solo una línea `MySQL not available, falling back to SQLite` en el log. Los datos de producción y los locales no están en ambas BD: permitir la IP en Hostinger → "Bases de datos MySQL remotas" si quieres trabajar contra la remota.
